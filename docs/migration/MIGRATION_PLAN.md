# chat-history 安装版迁移计划与难度评估

> 文档状态：已规划，未执行迁移。  
> 目标：将项目版安全部署为 ZCode 当前使用的安装版运行副本。  
> 原则：先备份、再影子验证、最后停机切换；生产数据优先于代码同步。

## 1. 当前现状与结论

| 项目 | 安装版 | 项目版 |
|---|---|---|
| 路径 | `~/.agent/tools/chat-history` | `<项目根>` |
| 角色 | ZCode 实际 MCP 运行副本 | 源码、测试和改动基线 |
| 入口 | 单体 `mcp_server.py` | 门面入口 + 多模块拆分 |
| Python | 3.14.0 | 3.14.0 |
| 核心依赖 | 已安装且与项目版实测一致 | 清单更严格、含测试所需依赖 |
| LanceDB | 约 835 MiB 生产数据 | 约 3 KiB 空/测试库 |
| 模型目录 | 约 4.58 GiB | 约 4.58 GiB |
| 标题缓存 | 旧 `title_fetcher.py` 协议，约 3.2 KiB | `title_cache.py` + `title_validate.py` 新协议，约 241 B |

### 结论

总体迁移难度为**中高**：代码迁移为中等，运行环境为低，生产 LanceDB 数据保护为高，标题缓存兼容为中高。迁移不应理解为“把项目目录复制到安装目录”，而应理解为“保留安装版运行资产，仅替换并验证项目版代码”。

## 2. 差异与迁移影响

### 2.1 入口架构

安装版的 `mcp_server.py` 仍包含配置、时间、数据库、检索、HTTP 和 MCP 接线；项目版已经拆出：

- `config.py`
- `timeutil.py`
- `db.py`
- `core.py`
- `errors.py`
- `http_server.py`
- `onnx_providers.py`
- `title_cache.py`
- `title_validate.py`
- `title_dispatcher.py`

因此部署时必须同步完整模块集合，不能只覆盖 `mcp_server.py`。

### 2.2 标题缓存

安装版依赖 `title_fetcher.py`；项目版已移除它，改为：

- `title_cache.py`：缓存读写、ZCode 源读取和持久化。
- `title_validate.py`：读取源并返回 0/1/2 状态。
- `title_dispatcher.py`：编排缓存命中、失效刷新和标题反向解析。
- `title_cache.json`：单一 `session_id -> title` 映射，反向查询由扫描推导。

旧缓存不能未经检查直接覆盖新缓存。迁移时应优先读取旧格式、转换为新平铺映射，并对条目数量、样本标题和重复标题进行校验；无法确认的条目允许由新校验逻辑重新学习。

### 2.3 依赖与模型

项目版将 NumPy 固定为 `2.5.2`，显式声明 `pyarrow>=25.0.1`，并增加 provider 配置说明；安装版清单仍较宽松。但两边虚拟环境实测均为 Python 3.14.0，LanceDB 0.38.0、MCP 2.1.1、tokenizers 0.23.2、NumPy 2.5.2、PyArrow 25.0.1 一致。因此默认复用安装版 `.venv` 和模型目录，不盲目重装或重新下载模型。

### 2.4 数据资产

安装版 `chat.db` 是生产库，约 874,752,380 字节；项目版 `chat.db` 不是迁移源，不能覆盖安装版。迁移第一原则是：**只替换代码和必要配置，不覆盖安装版 `chat.db`、模型目录和 `.venv`。**

### 2.5 ZCode 运行契约

`.zcode/cli/config.json` 当前把 `chat-history` MCP 指向安装版解释器、安装版 `mcp_server.py` 和安装版 `chat.db`。第一阶段不修改该配置，保持入口路径不变，以缩小变更面并保留简单回滚路径。

## 3. 风险分级

| 范围 | 难度 | 主要风险 | 控制措施 |
|---|---:|---|---|
| 源码同步 | 中 | 漏同步新模块或残留旧导入 | 按文件清单同步并做全量导入检查 |
| 虚拟环境 | 低 | 依赖清单和实际环境不一致 | 先记录版本，只在验证失败时补装 |
| 模型 | 低 | 误删或重新下载 | 只复用安装版模型目录 |
| 标题缓存 | 中高 | 旧格式、stale 刷新和重名语义变化 | 隔离路径转换、样本校验、保留旧备份 |
| LanceDB | 高 | 空库覆盖生产库、schema/索引破坏 | 生产库只备份不替换，切换前后校验 |
| 入口切换 | 中 | MCP 进程持有旧代码或 HTTP 端口冲突 | 停机确认、确认 17891 释放后启动 |
| 回滚 | 低中 | 备份不完整导致无法恢复 | 备份清单、SHA-256 和只读回滚冒烟 |

## 4. 迁移边界

### 目标

- 让项目版代码成为安装版运行副本。
- 保留安装版生产 LanceDB、模型、虚拟环境和 ZCode 调用契约。
- 验证 MCP、HTTP、标题解析和检索行为。

### 非目标

- 不重建 LanceDB 索引。
- 不迁移或修改 ZCode 主数据库。
- 不修改 MCP 工具签名。
- 不改变 hooks 行为。
- 不在本次迁移中处理 `remember` 幂等写入遗留项。
- 不将项目版空 `chat.db` 复制到安装版。

## 5. 分阶段迁移流程

### 阶段 0：前置检查

1. 确认 `.zcode/cli/config.json` 的 `chat-history` 仍指向安装版路径。
2. 确认安装版 MCP 进程、HTTP `17891` 使用状态，并安排短暂停机窗口。
3. 在项目版运行完整测试，记录通过、失败、跳过数量与耗时。
4. 记录两边 Python、依赖、模型目录、数据库大小、表结构和缓存文件哈希。
5. 确认安装版 `chat.db`、`models`、`.venv` 和 `title_cache.json` 可读。

### 阶段 1：备份

1. 在 `.agent/backups` 下创建带时间戳的新目录，不覆盖既有备份。
2. 备份安装版代码文件、`chat.db`、`title_cache.json`、`requirements.txt`、模型目录清单、`.venv` 版本信息。
3. 备份 `.zcode/cli/config.json`。
4. 生成备份清单，记录相对路径、大小和 SHA-256。
5. 数据库备份和哈希完成后，才允许进入切换阶段。

> 备份前不要删除旧文件；正式清理必须遵守可恢复删除规则。

### 阶段 2：兼容准备

1. 建立项目版到安装版的同步清单，至少包含所有 `.py`、`error_codes.json`、`requirements.txt` 和新模块。
2. 将旧 `title_fetcher.py` 作为待归档文件处理；不要在没有备份的情况下直接删除。
3. 在隔离目录读取旧 `title_cache.json`，转换为项目版单一 `id -> title` 映射。
4. 校验转换结果：条目数、重复标题、至少若干条按 ID 从 ZCode DB 读取的标题。
5. 保留安装版生产数据库；明确排除项目版 `chat.db`、测试产物和 `__pycache__`。
6. 默认复用安装版模型目录和 `.venv`，不做不必要的依赖重装。

### 阶段 3：影子验证

1. 不修改 `.zcode/cli/config.json`。
2. 将项目版代码放入临时影子目录，使用安装版 `.venv` 加载。
3. 将 `CHAT_HISTORY_DB` 指向生产库的只读副本。
4. 将 `TITLE_CACHE_PATH`、`ZCODE_DB_PATH` 指向隔离测试文件。
5. 验证：
   - 全量模块导入。
   - LanceDB schema 检查。
   - 模型懒加载和 embedding/reranker 初始化。
   - `/health`。
   - `list_sessions`、`recent`、`recall`。
   - 按 ID 取标题、按标题反向解析。
   - 标题源变化后的 state=2 刷新。
   - 标题不存在和重名错误码。
6. 影子验证期间禁止对生产库执行写入测试。

### 阶段 4：停机切换

1. 停止/退出加载安装版代码的 MCP 进程。
2. 确认 HTTP `17891` 已释放、没有正在进行的写入。
3. 再次确认安装版生产 `chat.db` 路径和大小。
4. 将项目版代码、配置 JSON、依赖清单和经过校验的标题缓存复制到安装版。
5. 不复制项目版 `chat.db`、模型目录或 `.venv`。
6. 使用临时目标目录准备文件后再切换，避免出现半套模块。
7. 将旧安装版文件先归档到备份目录，尤其是 `title_fetcher.py`。
8. 保持 `.zcode/cli/config.json` 中的安装版 `command`、`args` 和 `CHAT_HISTORY_DB` 不变。

### 阶段 5：切换后验证

1. 先执行只读启动验证：模块导入、schema、缓存加载和健康检查。
2. 验证 `list_sessions` 数量、最新消息时间和最新 turn 与切换前一致。
3. 验证 HTTP `17891` 可达。
4. 验证 hooks 可复用当前 MCP 服务。
5. 在隔离数据库上做最小 `remember` 写入验证；不要未经单独确认向生产库写入测试消息。
6. 回归标题缓存命中、未命中、stale 刷新、标题不存在和标题重名。
7. 记录切换前后数据库目录大小、表结构、行数/摘要、配置哈希和错误日志。

### 阶段 6：观察与回滚

观察窗口内出现下列任一情况，应停止新进程并回滚：

- 启动失败或 schema 错误。
- 标题查询大量返回空值、错误码异常或 stale 刷新失效。
- HTTP `17891` 端口冲突。
- `recall`/`recent` 明显异常或数据量突变。
- 生产数据库出现非预期写入、损坏或索引异常。

回滚顺序：

1. 停止新 MCP 进程。
2. 恢复安装版代码和旧标题缓存。
3. 如配置发生改动，恢复 `.zcode/cli/config.json`。
4. 使用原安装版 `.venv` 和模型目录启动。
5. 执行只读健康检查、`list_sessions` 和 `recent` 冒烟。
6. 保留迁移日志和失败现场，不删除生产数据。

## 6. 验收标准

迁移只有同时满足以下条件才算完成：

- 项目版完整测试集通过，失败数为 0。
- 安装版生产 `chat.db` 未被项目空库覆盖，表结构和数据摘要符合切换前记录。
- 项目版所有运行时模块均可导入。
- ZCode 配置仍能启动安装版入口，且未发生无关配置扩散修改。
- `/health`、`list_sessions`、`recent`、`recall` 正常。
- 标题缓存新格式可加载，反向解析、stale 刷新和错误码符合项目版设计。
- 没有不必要的依赖重装、模型重下载或数据库重建。
- 备份、哈希、测试、切换、观察和回滚记录完整。

## 7. 推荐执行顺序

1. 评审本计划文档。
2. 建立安装版与配置备份。
3. 做标题缓存隔离转换和影子验证。
4. 运行项目测试及生产库只读验收。
5. 安排停机窗口并切换代码。
6. 执行切换后验证和观察。
7. 仅在验收通过后保留新版本；否则按回滚顺序恢复。

## 8. 严禁事项

- 直接把项目版整个目录覆盖安装版。
- 把项目版空 `chat.db` 覆盖安装版生产库。
- 先改 `.zcode/cli/config.json` 指向项目版。
- 没有备份和停机确认就写入/转换生产标题缓存。
- 把文件复制成功当成迁移成功。
